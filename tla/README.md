# TLA+ specification — ReasonMesh AKX protocol

This directory contains a TLA+ formal model of the ReasonMesh distributed clause-sharing protocol. The model verifies the AKX network layer: the BroadcastBus dual-queue design, bridge thread forwarding, TCP delivery, and peer import. It does not model the CDCL search engine — that is abstracted as a nondeterministic oracle.

---

## Files

| File | Purpose |
|---|---|
| `ReasonMesh.tla` | Main spec: state variables, actions, fairness, invariants, liveness properties |
| `MC.tla` | Concrete model: 2 nodes, 3 clauses, Timeout enabled |
| `MC.cfg` | TLC config for `MC`: safety + weak liveness (L1-L4, L8, I8) |
| `MC_NoTimeout.tla` | Variant with the Timeout action removed |
| `MC_NoTimeout.cfg` | TLC config for `MC_NoTimeout`: adds strong liveness (L5-L7) |
| `tla2tools.jar` | TLC model checker; run directly with `java -cp` |

The `MC_TTrace_*.tla` files are trace explorer outputs generated by the TLA+ Toolbox. They record specific state sequences from past TLC runs and can be replayed to step through an execution path. They are not part of the proof — ignore them unless you are debugging a specific counterexample.

## Prerequisites

Java 11 or later. `tla2tools.jar` is required but not tracked in this repository (it is a 4.4 MB binary). Download the latest release from the TLA+ GitHub releases page:

```sh
curl -L -o tla/tla2tools.jar \
  https://github.com/tlaplus/tlaplus/releases/latest/download/tla2tools.jar
```

Check your Java version:

```sh
java -version
```

## Running TLC

All commands assume you are in the `tla/` directory:

```sh
cd tla
```

### Safety + weak liveness (Timeout enabled)

This is the primary check. It verifies all seven safety invariants and liveness properties L1–L4, L8, and temporal safety I8 across 46,099 distinct states.

```sh
java -XX:+UseParallelGC -cp tla2tools.jar tlc2.TLC MC -config MC.cfg -workers auto
```

Expected output (abbreviated):

```
Model checking completed. No error has been found.
290381 states generated, 46099 distinct states found, 0 states left on queue.
The depth of the complete state graph search is 24.
Finished in 02min 20s
```

`-workers auto` uses one thread per available CPU core. On a machine with fewer than 8 cores, runtime will be proportionally longer. On 4 cores, expect around 4–5 minutes.

### Strong liveness (Timeout disabled)

Removes the `Timeout` action so that the only path out of "searching" is solving. This is needed to check L5 (key clauses propagate to all nodes), L6 (proof leads to verdict), and L7 (eventually all nodes prove UNSAT), because all three are falsified by Timeout — a node can time out before receiving shared clauses, and that is a valid behavior.

```sh
java -XX:+UseParallelGC -cp tla2tools.jar tlc2.TLC MC_NoTimeout -config MC_NoTimeout.cfg -workers auto
```

Expected output (abbreviated):

```
Model checking completed. No error has been found.
196909 states generated, 34661 distinct states found, 0 states left on queue.
The depth of the complete state graph search is 24.
Finished in 02min 01s
```

The state space is smaller than the main check because Timeout adds transitions that the no-timeout model doesn't have — more paths to explore in MC.

## What is being checked

### Safety invariants (I1–I7)

All checked as `INVARIANT Safety` in both configs. A violation would produce a counterexample trace showing the exact state sequence leading to the violation.

| ID | Name | What it means |
|---|---|---|
| I1 | `TypeOK` | All variables have the types declared in the spec |
| I2 | `UnsatRequiresProof` | A node reports UNSAT only if it holds all key clauses |
| I3 | `FilterIntegrity` | Only high-utility clauses appear in export queues and TCP channels |
| I4 | `ExportQueueSound` | The bridge cannot forward a clause the node has not yet learned |
| I5 | `InFlightSound` | Clauses in transit were learned by the sender before transmission |
| I6 | `LocalQIntegrity` | Clauses in the import queue came from the network (high-utility only) |
| I7 | `NoSelfForward` | A node's bridge never sends to itself |

I1–I5 were in the original spec. I6 and I7 were added to name structural properties that the spec guarantees but didn't previously assert.

### Liveness properties (L1–L8)

Checked as `PROPERTY` in both configs. These require the `Fairness` assumptions in the spec — WF (weak fairness) on the infrastructure actions and SF (strong fairness) on key-clause learning. A violation would produce a counterexample behavior, which is an infinite execution that violates the leads-to formula.

| ID | Name | Condition | Config |
|---|---|---|---|
| L1 | `ClausesEventuallyForwarded` | Export queue always drains | both |
| L2 | `ClausesEventuallyDelivered` | In-flight clauses always arrive | both |
| L3 | `EventualTermination` | Every node eventually terminates | both |
| L4 | `ConvergentTermination` | One UNSAT proof terminates the fleet | both |
| L5 | `KeyClausesPropagateToAll` | Key clauses spread to every node | no-timeout only |
| L6 | `ProofLeadsToVerdict` | Accumulating the proof leads to UNSAT | no-timeout only |
| L7 | `EventuallyAllUnsat` | The entire fleet eventually agrees on UNSAT | no-timeout only |
| L8 | `ClausesEventuallyImported` | Import queue always drains | both |

L8 was added to close the end-to-end pipeline proof: L1 covers `export_q → in_flight`, L2 covers `in_flight → local_q`, and L8 covers `local_q → learned`.

### Temporal safety (I8)

`VerdictMonotone` is checked as a `PROPERTY` (not `INVARIANT` because it involves `[]`, the always operator). It says: once a node reaches "unsat" or "timeout", it stays there forever. This is structurally guaranteed by the spec (the only actions that change `verdict` are `ReportUnsat` and `Timeout`, both of which guard on `verdict[n] = "searching"`), but naming it here means future spec changes that accidentally break the guard will be caught by TLC.

## What is not modelled

**Cube-and-conquer lease protocol.** The coordinator (rm-coordinator) and node (rm-node) regime A — where a formula is recursively partitioned and workers solve sub-cubes under different assumptions — requires a separate spec. The `ImportGate` assumption-scoped predicate is the key piece: a clause learned under assumptions `A` may only be imported by a worker whose assumption set is consistent with `A`. Modelling this correctly requires cube-state variables and an assumption-compatibility relation, which would roughly double the spec size. That spec is future work.

**Clause queue ordering.** `InprocBus` implements utility-based eviction (lowest-utility item evicted when the queue is full). The spec models the queue as a set, which is a sound over-approximation: it allows any subset of clauses to be present, including cases where all clauses survive (no eviction). This means the spec does not falsify liveness in the scenario where a useful clause is repeatedly evicted before it can be forwarded. That property requires reasoning about the utility ordering, which is out of scope for this boolean-abstraction model.

**Network loss and reordering.** The `NetDeliver` action models TCP as reliable in-order delivery (a clause in `in_flight` eventually arrives, in the fairness sense). Real TCP is reliable, so this is accurate for the intended deployment. Lossy networks would require a `Drop` action and would falsify L2 and L5.

## Model parameters

The concrete model in `MC.tla` uses the smallest parameter set that exercises all relevant behaviors:

```
NODES        = {"n1", "n2"}      -- two peers is the minimum for sharing
CLAUSES      = {"c1", "c2", "c3"}
KEY_CLAUSES  = {"c1", "c2"}      -- UNSAT requires both; c3 is a non-key bonus
HIGH_UTILITY = {"c1", "c2", "c3"} -- all three pass the bridge filter
```

`c3` is high-utility but not a key clause. This tests that:
- The bridge forwards c3 (it is high-utility)
- Accumulating only c3 does not trigger a spurious UNSAT verdict (I2 holds)

If you want to check the model at larger scale, increasing `CLAUSES` and `KEY_CLAUSES` will cause an exponential blowup in state space. Adding a third node roughly doubles the state count again. The 2-node / 3-clause model is deliberately chosen to finish in under 3 minutes on a laptop.

## Understanding TLC output

TLC reports the number of reachable states and the diameter (longest shortest path from Init to any state). For the current model:

- **46,099 distinct states** (MC): every state reachable from Init under all possible interleavings of all actions.
- **34,661 distinct states** (MC_NoTimeout): fewer because Timeout generates many additional paths that MC must explore.
- **Depth 24**: the longest behavior before all nodes have reached terminal verdicts takes at most 24 steps. This is consistent with: 3 clauses × 2 nodes = 6 LearnClause steps + 3 BridgeForward + 3 NetDeliver + 3 WorkerImport + 2 ReportUnsat/Timeout = ~17 meaningful steps, plus some interleaving overhead.

The "implied-temporal checking" line reports how many branches TLC must evaluate to check the liveness properties. More properties = more branches. The branch count grew from 21 to 31 (MC) and from 32 to 42 (MC_NoTimeout) when `ClausesEventuallyImported` and `VerdictMonotone` were added.

## Using the TLA+ Toolbox (GUI)

If you prefer a graphical environment:

1. Download the TLA+ Toolbox from [https://lamport.azurewebsites.net/tla/toolbox.html](https://lamport.azurewebsites.net/tla/toolbox.html).
2. Create a new spec, pointing at `ReasonMesh.tla`.
3. Create a model, using `MC.tla` for the concrete parameters.
4. In the model editor:
   - Set the specification to `Spec`
   - Add `Safety` as an invariant
   - Add each liveness property as a property
5. Run the model. The Toolbox uses `tla2tools.jar` internally.

The Toolbox's trace explorer lets you step through a counterexample state by state — useful if you modify the spec and TLC finds a violation.
